# 理稿台 设计文档（一期「理清」+ 二期「取舍」）

- 日期：2026-09-10
- 状态：已通过审阅（2026-09-11）
- 界面原型：`docs/prototype/ligaotai-prototype.html`（在线版 https://claude.ai/code/artifact/fe38e1f7-8b3e-4f2c-a8ba-f802a9073fc8）

## 1. 要解决的问题

作者有一部约 200 万字的长篇手稿，本来是一本书，但现在很乱：

- 手稿是很多零散文件，有的是章节，有的是片段，有的是设定笔记，文件名不规范，顺序不明。
- 同一本书里有好几个「世界」和好几条没写完的支线。
- 同一个场景可能写过好几版，人物叫法前后不统一，设定前后矛盾。
- 任何 AI 的上下文都装不下全书，所以没法系统地帮他成书。

最终目标分三步：**理清 → 取舍 → 补写**。本文档覆盖前两步（一期、二期），补写（三期）只写接口预留，单独再出设计。

## 2. 核心思路：分层压缩

AI 一次读不完全书，所以把全书压成四层，每层都能装进一次对话：

| 层 | 内容 | 体量（200 万字的书） |
|---|---|---|
| L0 原文 | 切成场景块，每块有固定编号，永不修改 | 200 万字 |
| L1 场景卡 | 每块一张结构化卡片 | 约 1/10 |
| L2 档案 | 每条支线一份档案、每个世界一份设定集 | 每份几千字 |
| L3 全书地图 | 全书总览 | 约 2 万字 |

- 理清 = 从 L0 往上逐层压。
- 取舍 = AI 在 L3、L2 上和作者讨论，产出成书骨架。
- 补写（三期）= 从上往下按需取材料，拼成「材料包」喂给 AI。

**铁律：AI 产出的东西一律先是「草稿」，作者确认后才算数。AI 永远不覆盖作者确认过的内容。**

## 3. 范围

### 一期 · 理清
导入、切场景、查重、场景卡、实体合并、归线排序、档案 + 矛盾 + 地图，共 7 步流水线；以及全景、场景浏览、实体合并确认、归线确认、矛盾裁决、设定库、设置这些页面。

### 二期 · 取舍
取舍看板、影响检查、定稿设定、成书骨架（生成 + 编辑）、按骨架导出拼好的全书。

### 不做（YAGNI）
- 补写、改写、润色（三期）。
- 在软件里编辑原稿正文（一、二期原稿只读）。
- 从写作平台（起点、番茄、飞卢等）直接导入。作者要求先不管，用户自己导出成文件再导入。
- 导出 docx、EPUB（二期只导出 md 和 txt）。
- 多用户、云端、手机端。

## 4. 总体架构

```
浏览器（Vue 3 单页）  ⇄  本机 FastAPI 服务（127.0.0.1）  ⇄  书库文件夹（md / json）
                                   ⇅
                         OpenAI 兼容接口（默认 DeepSeek）
```

- **后端**：Python 3.11+、FastAPI。后台任务用进程内任务队列（asyncio），一次只跑一个流水线任务，任务内部并发调用模型。
- **前端**：Vue 3 + Vite，构建成静态文件，由 FastAPI 托管。运行时不需要 Node。
- **存储**：**文件就是数据源**，不用数据库。每本书一个文件夹，用 Obsidian 也能直接打开。启动时把场景卡等读进内存建索引（1000 多张卡，几 MB，全放内存没问题）。
- **启动**：双击 `启动理稿台.bat`（正文纯 ASCII，按全局规矩），会起服务并打开浏览器。
- **只监听 127.0.0.1**，不对外网开放。

## 5. 数据布局

```
<书库目录>/<书名>/
  book.json            书的元信息、流水线各步状态
  原稿/                导入原件的副本，按原目录结构保存，只读
  场景/S-0001.md       每个场景块的正文（带来源文件和位置的头信息）
  场景卡/S-0001.json   L1 场景卡
  版本组.json          查重结果
  实体.json            人物、地点、组织的规范名和别名（含确认状态）
  世界与支线.json      世界划分、支线划分、线内顺序、故事时间估计（含确认状态）
  档案/支线/*.md       L2 支线档案
  档案/世界/*.md       L2 世界设定集
  矛盾.json            矛盾清单及裁决
  定稿设定.json        作者裁决后的正式设定（二期起，三期补写要遵守）
  全书地图.md          L3
  取舍/看板.json       二期：每条线的去留
  取舍/骨架.json       二期：成书骨架
  导出/                二期：按骨架拼好的全书
  日志/                每次模型调用的请求和返回（便于排错）
```

应用级配置（**不在书文件夹里**，这样分享书文件夹不会带出 key）：`<应用目录>/config.json`，内容包括书库目录、接口地址、模型名、API key、并发数、单价（用来估算费用）。

### 5.1 场景编号
- 按导入时的「文件路径排序 + 文件内位置」依次编号：`S-0001`、`S-0002`……
- 每块记录内容哈希。以后追加导入新文件，接着往后编号，不重排旧编号。
- 某块原文的哈希变了（作者在外面改了原件后重新导入），它的场景卡标记为「过期」，下次流水线只重跑过期的块。

### 5.2 场景卡字段（L1）
```json
{
  "id": "S-0102",
  "summary": "≤150字，发生了什么",
  "pov": "视角人物",
  "characters": [{"name": "原文里的叫法", "role": "主要|次要|提及"}],
  "locations": ["原文里的地名"],
  "world_hint": "AI 判断属于哪个世界的依据（原文线索）",
  "time_hints": ["原文里的时间表述，照抄"],
  "events": ["关键事件，每条一句"],
  "facts": [{"subject": "林清", "attribute": "年龄", "value": "十六", "quote": "林清年方十六"}],
  "hooks_planted": ["埋下的伏笔/悬念"],
  "hooks_resolved": ["回收的伏笔"],
  "refs_elsewhere": ["提到但本块没写的事件，如「青州城破」"],
  "incomplete": false,
  "incomplete_note": "写到一半的说明",
  "kind": "正文|提纲|设定笔记|碎片"
}
```
`facts` 必须带原文引用，这是后面查矛盾的依据；`refs_elsewhere` 是后面找「缺口」的依据。

## 6. 一期流水线（7 步）

每一步都**逐项落盘**：每处理完一块就写一个文件，所以中断后重跑会跳过已完成的项。每步的状态记在 `book.json`。上游确认的结果一改，下游受影响的部分标记为过期。

| 步 | 名称 | 花 AI 钱 | 要作者确认 |
|---|---|---|---|
| 1 | 导入 | 否 | 否 |
| 2 | 切场景 | 否 | 否 |
| 3 | 查重 | 否 | 可选 |
| 4 | 场景卡 | 是 | 否 |
| 5 | 实体合并 | 是 | **是** |
| 6 | 归线排序 | 是 | **是** |
| 7 | 档案 + 矛盾 + 地图 | 是 | 矛盾逐条裁决 |

### 步骤 1 · 导入
- 支持 `.txt` `.md` `.docx`。txt 自动识别编码（UTF-8 / GBK / GB18030，用 `charset-normalizer`）。docx 用 `python-docx` 取正文段落和标题样式。
- 选一个文件夹，递归导入，原件复制到 `原稿/`。
- 其他格式的文件跳过，并在结果里列出来。

### 步骤 2 · 切场景
按优先级依次切：
1. 章节标题：`第X章/节/回/卷`、`Chapter N`、Markdown `#`、docx 标题样式、单独一行的数字编号。
2. 显式分隔符：`***`、`———`、`◇◇◇`、连续空行 ≥2 等（规则表可配置）。
3. 仍超过 5000 字的块，在最接近 3000 字处的空行切开。
4. 不足 300 字的块保留为独立块，标记 `kind` 候选为「碎片」，不和别的块硬合并（碎片本身就是有用的信息）。

每块保留来源文件路径和起止位置，界面上能跳回原件看。

### 步骤 3 · 查重
- 用字符 5-gram 的 MinHash + LSH（`datasketch`）找相似块，默认 Jaccard ≥ 0.5 算同一场景的不同版本，阈值可调。
- 另外检查包含关系：短块基本都出现在长块里，也归为同一组。
- 每个版本组默认选一块当「主版本」（优先最长，其次文件修改时间最新），作者可以改。**只有主版本参与第 6 步归线**，其余版本挂在主版本下面，界面上可以并排对比。

### 步骤 4 · 场景卡
- 每块单独调用一次模型，按 5.2 的字段输出 JSON（`response_format: json_object`），用 pydantic 校验。
- 各块并行跑，互不依赖。人名、地名照原文抄，不在这一步统一（统一放到第 5 步）。
- 校验失败会把错误信息反馈给模型重试，最多 3 次；还不行就标为「失败」，列出来可以单独重跑。

### 步骤 5 · 实体合并（作者确认）
1. 汇总所有卡片里出现的人名、地名、组织名，统计出现次数和出现场景。
2. 程序先找候选组：同姓 + 同字、称谓模式（「林姑娘」「清儿」）、字符串相似、总在同一场景出现却从不同时说话等。
3. 把候选组连同每个名字的几句上下文分批交给模型判断：是不是同一个人，规范名叫什么，理由是什么。
4. 界面上逐组确认：合并、拆开、改规范名。作者也可以手动把两个名字拖到一起。
5. 确认结果写进 `实体.json`，之后所有步骤一律用规范名。

### 步骤 6 · 归线排序（作者确认）
把每张主版本卡压缩成一行（编号 + 摘要 + 规范人物 + 地点 + 世界线索 + 时间线索），1000 多块约 13 万字，一次调用装得下（deepseek-flash 窗口约 100 万 token）。
1. **划分世界**：整书一次调用，把场景分到各个世界，输出每个世界的判定依据。
2. **划分支线**：每个世界一次调用，把场景聚成支线，并指定一条主线。
3. **线内排序 + 故事时间**：每条支线一次调用，给出线内顺序，以及每块的故事时间估计（数值 + 单位 + 置信度，单位由模型按本书提议，比如「年」）。
4. **跨线对齐**：用共同事件、共同出场人物，把各条线的故事时间对齐到同一根轴上，并标出和主线的交汇点。
5. **断点和缺口**：每条线判断写到哪停了（断点）、完结还是待定；再把 `refs_elsewhere` 里提到却找不到对应场景的事件，标成「缺口」。

作者在界面上确认：把场景拖到别的线、合并或拆分支线、改线名、调整顺序。确认后写进 `世界与支线.json`。

**大书保护**：如果压缩后的全书卡片超过配置的上限（默认 60 万 token），第 1 步改为分段划分再合并，避免超出窗口。

### 步骤 7 · 档案 + 矛盾 + 地图
1. **支线档案**（每条线一次调用）：来龙去脉、写到哪、断点、缺口、开放的伏笔、主要人物，引用都带场景编号。
2. **世界设定集**（每个世界一次调用）：从这个世界所有卡片的 `facts` 汇总。
3. **矛盾扫描**：把全部 `facts` 按（规范主语, 属性）分组，值不一致的组交给模型判断：是真矛盾，还是随故事时间合理变化（比如年龄增长、换了佩剑）；再给出严重程度（严重 / 中等 / 轻微）和分类（人物 / 设定 / 时间 / 称谓）。另外检查故事时间线上的冲突。
4. **全书地图**：用全部档案生成 L3，约 2 万字。

## 7. 二期 · 取舍

### 7.1 取舍看板
- 每条线一张卡：字数、场景数、完成度、状态、AI 建议（保留 / 合并到某线 / 砍掉 / 改成回忆等）和理由。
- 四列：保留、合并、砍掉、还没想好。作者拖动决定，写进 `取舍/看板.json`。
- **影响检查**：卡片拖进「砍掉」或「合并」时，先算出会断掉什么。程序化部分从数据里直接算（这条线里埋下、在别的线回收的伏笔；和主线的交汇点；只在这条线出场的人物；别的线里引用这条线事件的场景）；再由模型补一段话，说明影响和建议的补救办法。

### 7.2 矛盾裁决与定稿设定
- 矛盾页的每一条：以左边为准 / 以右边为准 / 都不对自己写一句 / 先放着。
- 裁决结果写进 `定稿设定.json`，每条带来源场景编号。三期补写必须遵守这里的内容。
- 裁决会顺带列出受影响的场景（「选定后另一版要跟着改这 12 处」），二期只记录，不改原文。

### 7.3 成书骨架
- 作者把看板定下来后，模型根据留下的线、合并关系、定稿设定排出骨架：卷 → 章 → 每章用哪几块现成场景（按编号引用），缺的地方插入「空洞」。
- 每个空洞带一段任务说明：在哪两块之间、要写什么、大纲或别处引用里提过什么。三期补写直接用这段说明。
- 骨架可以编辑：改卷名和章名、拖动章节顺序、在章之间移动场景、增删空洞。
- 写进 `取舍/骨架.json`。

### 7.4 导出
按骨架把现成场景拼成一本，导出为 md 和 txt，空洞处插入醒目的占位说明。这样作者在补写之前，就能先从头到尾读一遍「理过的书」。

## 9. 模型接入

- 走 OpenAI 兼容的 Chat Completions 接口。默认 `https://api.deepseek.com`、模型 `deepseek-flash`（2026-09-10 查官方价格页：窗口 100 万 token，支持 JSON 输出；`deepseek-v4-pro` 已弃用，9 月 14 日起转到 Flash）。模型名可自由改，不写死。
- 按任务分两档模型配置：「批量」（场景卡、实体初筛）和「综合」（归线、档案、矛盾判断、骨架）。默认两档都用 deepseek-flash，以后可以把综合档换成更强的模型。
- 并发默认 8；遇到 429 / 5xx 指数退避重试；单次调用超时 120 秒。
- 从接口返回的 usage 统计 token，连同按单价算出的费用一并记进 `book.json`（`tools/eval_*` 要用）。**界面不显示任何费用数字，也不做事前估价**——估价在本项目里反复失准（②b 估 $1.32 实花 $1.57；②c Task 24 计划里的「约 $0.3」真实是 $2.77～$4.15），作者 2026-09-21 拍板去掉。详见计划③ spec 第 7.3 节。
- 提示词放在应用的 `prompts/` 目录，一个任务一个文件，方便调。
- 这是理稿台自己的配置，和 Claude Code 的配置无关。

## 10. 出错处理

| 情况 | 处理 |
|---|---|
| 模型返回的 JSON 不合格 | 带错误信息重试，最多 3 次，仍失败就标为失败项，可单独重跑 |
| 网络断、限流 | 退避重试；任务可以暂停和继续；已落盘的项不重跑 |
| 程序中途崩溃或关机 | 下次启动时读 `book.json` 和已落盘文件，从断点继续 |
| 作者改了上游的确认结果 | 下游受影响的部分标记为过期，只重跑受影响的线或世界 |
| 原件在外面被改动后重新导入 | 按哈希找出变化的块，这些块的卡片过期，只重跑它们 |
| key 没配或配错 | 设置页「测试连接」直接报错原因；流水线里需要 AI 的步骤在开始前拦住 |
| 模型漏掉某些场景（归线时没分配） | 程序校验覆盖率，没被分配的场景单独列出来，交给作者或补一次调用 |

## 11. 测试与验收

### 11.1 单元测试
切场景规则、编码识别、查重、编号稳定性（追加导入不重排）、场景卡 JSON 校验、过期传播、影响检查的程序化部分。

### 11.2 集成测试
用录制好的假模型返回（fixtures）把 7 步流水线和二期流程完整跑一遍，不花钱，放进 CI。

### 11.3 验收：人造乱稿
写一个「弄乱」脚本，拿公版书《西游记》（约 80 万字）制造一份带标准答案的乱稿：
- 拆成几百个文件，打乱文件名和顺序；
- 随机挑章节生成改写版，当作「同一场景的第二版」；
- 给主要人物替换别名（如「悟空 / 猴王 / 行者 / 孙大圣」本来就有，再加几个）；
- 删掉若干章，制造缺口；截断若干章，制造「写到一半」。

用真模型跑一遍，对照标准答案：

| 指标 | 门槛 |
|---|---|
| 植入的重复版本被找到 | ≥ 90% |
| 植入的别名被提议合并 | ≥ 90% |
| 线内顺序与原书顺序的 Kendall τ | ≥ 0.8 |
| 被删章节被标成缺口 | 只记录，不设门槛（这一项难，先看实际水平） |
| 矛盾扫描 | 只记录，人工抽查 20 条的准确率 |

验收通过后，再用作者的真稿跑。

## 12. 三期预留（补写，本期不做）

- 数据：骨架里的「空洞」和任务说明、`定稿设定.json`、档案、场景卡都已具备，三期直接使用。
- 材料包：地图 + 相关档案 + 相关人物卡 + 定稿设定 + 前后原文 + 作者文风样本，作者可以增减，并显示窗口占用。
- 文风用作者原文当样例，不用规则描述（已有实测：否定式指令无效，给样例才有效）。
- 一次出多个版本，自动对照定稿设定做一致性检查；采纳后生成场景卡、更新档案，同样先当草稿。

## 13. 参考过的现成项目

- NovelWriter（Hurricane0698/novelwriter）：「提取结果先当草稿、确认后入库」「按相关性注入设定而不是塞全书」两条原则。
