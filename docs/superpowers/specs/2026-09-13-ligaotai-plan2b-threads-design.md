## 2. 步骤 6 的流程

所有调用走综合档模型（默认开思考模式 high）。

### 2.0 准备

- **只取主版本块**：不在任何版本组里的块，加上每个版本组的 `main`。非主版本不参与归线，挂在主版本下面。
- 已标 `removed` 的块跳过；没有场景卡、或者卡已过期（`scene_hash` 对不上）的块不参与，直接列进「未分配」，原因写「没有可用的场景卡」。
- **每张卡压成一行**：`编号｜类型｜摘要｜人物｜地点｜世界线索｜时间线索`。人物、地点、组织一律换成 `实体.json` 里的规范名（草稿组也换）；找不到映射的保留原文叫法。
- 按类型分三类：
  - **正文、碎片**：进支线、参与排序。
  - **提纲**：挂在它讲的那条线上当参考，不排序（步骤 7 找缺口、写档案要用）。
  - **设定笔记**：只归到世界，不进任何支线。
  - 类型是步骤 4 模型判的，可能判错，作者可以手动挪。

### 2.1 划世界（整书 1 次调用）

- 输入：全部行。
- 输出：世界列表（名字 + 判定依据）、每个世界包含哪些块、**全书统一的故事时间单位**（模型按本书提议，比如「年」「天」）。
- 输出格式用「世界 → 编号列表」，别用「每块一条」，省输出 token。
- **大书保护**：估算的输入 token（按 1 个字符算 1 个 token，偏保守）超过上限（新增本书参数 `threads_max_input_tokens`，默认 600000）时分段：按编号顺序切成几段依次调用，后一段带上前面已有的世界列表，可以归入已有世界，也可以新开世界。

### 2.2 划支线（每个世界 1 次）

- 输入：这个世界的全部行。
- 输出：支线列表（名字 + 一句话说明）、每条线包含哪些正文 / 碎片块、每个提纲块挂在哪条线（挂不上的留在世界下面）。
- 每个世界的调用都指定一条本世界的主线；**全书主线**取块最多的那个世界的主线，作者可以改。
- 一个世界的行超过上限时，照 2.1 的办法分段。

### 2.3 线内排序（每条线 1 次）

- **片段**：同一个源文件里文件内位置相邻、都在这条线里、都是正文或碎片的块，绑成一个片段（编号 `P-001`…，只在这次调用里有效）。碰到提纲、设定笔记、非主版本、别的线的块就断开。
- 输入：这条线的片段和单块。每个片段标明「这几块在同一个文件里紧挨着，原文顺序是……」。
- 输出：
  - 顺序：列表里的每一项可以是片段编号（整段按原文顺序放进去），也可以是单块编号。模型觉得一个片段接不上，可以把它拆成单块分别放。
  - 每块的故事时间：数值 + 把握（高 / 中 / 低），单位用 2.1 定的。
  - 这条线的结局：完结还是待定，断点说明（写到哪停了）。
- 这次调用失败（重试完还不行）时，这条线按「源文件路径 + 文件内位置」排，标上「排序失败，按原稿位置暂排」。

### 2.4 跨线对齐（全书 1 次）

- 输入：每条线按顺序排好的行，带线内故事时间。
- 输出：每条线的时间偏移（全书时间 = 线内时间 + 偏移），对不上的留空；每条线和全书主线的交汇点（哪一块对哪一块，理由）。
- 失败时所有偏移留空、交汇点为空，记在失败清单里，整步不失败。

### 2.5 缺口（每个世界 1 次）

- 输入：这个世界的线（按顺序排好的行），加上这个世界所有卡片的 `refs_elsewhere`（带出处块）。
- 输出：找不到对应场景的事件标成缺口，写明是哪个事件、哪几块提到它、大概在哪条线的哪两块之间。
- 失败时这个世界没有缺口，记在失败清单里。

### 2.6 每次调用的共同规则

- **覆盖校验**：输出必须把输入的编号恰好覆盖一遍（2.3 里片段编号也算覆盖）。漏了、重复了、出现输入里没有的编号，都把问题反馈给模型重试，最多 3 次。3 次后还有问题：编造的编号丢掉，重复的留第一次出现的，漏掉的进「未分配」，原因写「模型没分配」。
- **缓存**：每次调用的结果按「系统提示 + 用户输入 + 模型配置」的哈希缓存到 `归线缓存.json`，做法同 ②a 的实体合并缓存。暂停、崩溃、重跑，输入没变的调用都不再花钱；跑成功后清掉这次没用到的条目。
- **暂停 = 取消任务**，同 ②a。
- 欠费、key 失效（`FatalLLMError`）直接让整步失败，报给作者。
- 提示词放 `prompts/`，一步一个文件：`threads_worlds.md`、`threads_lines.md`、`threads_order.md`、`threads_align.md`、`threads_gaps.md`。

## 3. 数据：`世界与支线.json`

```json
{
  "next_world": 3,
  "next_thread": 7,
  "time_unit": "年",
  "main_thread": "L-001",
  "worlds": [
    {"id": "W-01", "name": "……", "reason": "判定依据", "status": "draft", "notes": ["S-0040"], "outlines": ["S-0077"]}
  ],
  "threads": [
    {
      "id": "L-001", "world": "W-01", "name": "……", "about": "一句话说明",
      "status": "draft",
      "scenes": ["S-0003", "S-0004", "S-0120"],
      "times": {"S-0003": {"t": 0, "conf": "高"}},
      "outlines": ["S-0077"],
      "offset": 0,
      "end": {"state": "待定", "note": "断点说明", "last": "S-0120"},
      "order_failed": false
    }
  ],
  "intersections": [{"thread": "L-002", "scene": "S-0150", "main_scene": "S-0004", "reason": "……"}],
  "gaps": [{"id": "Q-001", "world": "W-01", "thread": "L-001", "event": "青州城破", "mentioned_in": ["S-0150"], "after": "S-0004", "before": "S-0120"}],
  "unassigned": [{"scene": "S-0200", "reason": "没有可用的场景卡"}],
  "pending": [{"scene": "S-0210", "thread": "L-001", "reason": "模型建议归入已确认的线"}]
}
```

- `notes`：世界下面的设定笔记；世界下面的 `outlines`：挂不上任何线的提纲。
- `status`（线和世界都有）：`draft`（模型草稿）/ `confirmed`（作者确认或动过）。世界在作者改了它的名字、或者它下面有已确认的线时算 `confirmed`。
- 世界、线的编号取文件顶层只增不减的 `next_world` / `next_thread`（②a 实体编号踩过撞号的坑）。同一个世界 / 线重跑后成员没变就沿用原编号。
- 同时写 `book.json` 里步骤 `threads` 的 summary：世界数、线数、未分配数、建议归入数、缺口数、失败的调用、调用次数、费用。

## 4. 作者调整（后端接口，界面在计划③）

| 操作 | 说明 |
|---|---|
| 确认线 | 成员、顺序、时间锁定 |
| 改名 | 线或世界 |
| 挪块 | 把若干块放到某条线的某个位置；同一条线里挪就是调顺序；也用来把「未分配」「建议归入」「世界下面的笔记 / 提纲」放进线 |
| 合并线 | 合成第一条，顺序按第一条在前、其余接在后面，作者再调 |
| 拆线 | 从某一块起，后面的拆成一条新线 |
| 设主线 | 全书主线换成另一条 |
| 挪线 | 把一条线挪到别的世界 |

- 作者动过的线自动变成 `confirmed`（同 ②a 的实体）。
- 每个操作的「读 → 改 → 写」都在 `FILE_LOCK` 里；内容真的变了才把下游（步骤 7）标过期。
- 挪空了的线删掉；世界下面没有线、没有笔记也没有提纲了就删掉。

## 5. 重跑与过期

- **确认过的线原样保留**：成员、顺序、时间都不动。重跑时锁住的块不进 2.1 / 2.2 的输入；已确认的线作为「已有的线」（名字 + 所属世界 + 几行摘要）告诉模型。
- **模型想往已确认的线里加新块**：不改那条线，放进 `pending`，等作者点头。
- **已确认的世界保留**（名字、编号不变）；新块可以归入它，也可以新开世界。草稿世界每次重算。
- **过期**：场景卡变了、实体规范名映射变了、主版本换了，步骤 6 标过期（沿用现有的 `_outdate_after`）。
- **跑的途中上游变了**（已知问题文档「计划②b 要处理的」那条）：开跑时算一个输入指纹（规范名映射 + 各版本组主版本 + 参与块的卡片 `scene_hash`），跑完再算一次；两次不一样，这一步记成 `outdated`，不记 `done`。

## 6. 验收

### 6.1 两本书

| 书 | 用途 | 跑哪些步骤 |
|---|---|---|
| 西游记（②a 那本验收书） | 底线：流程跑得通、没排乱 | 只跑步骤 6，场景卡和实体沿用 |
| 冷门书（默认《雪月梅傳》，古腾堡 26739，50 回约 26 万字） | 真正看排序能力 | 弄乱 → 导入 → 切场景 → 查重 → 场景卡 → 实体 → 归线 |

**为什么要加冷门书**：西游记太有名，模型背得出情节顺序，排出来的一部分是记忆，不全是读卡片推的，在西游记上测出来的 τ 会比作者的真稿好看。

- **先测模型熟不熟**：真跑前不给任何原文，只问模型「《雪月梅傳》各回讲了什么，按顺序列出」，花几分钱。能大致按顺序说出多数回目情节，就换备选《天豹圖》（古腾堡 26904，40 回约 19 万字），再测一遍。
- **弄乱**：`tools/scramble.py` 加 `--aliases`（一个 JSON 文件，格式同 `DEFAULT_ALIASES`），给冷门书三个主要人物换别名，别名读完原文再挑。其余参数同西游记：删 5 回、截断 5 回、整回副本 10 个、片段副本 5 个。

### 6.2 指标

- **标准位置**：每块从 `source` 查到答案里的文件，拿到（第几回，第几片），再加块在文件里的位置，就是它在原书里的位置。
- **线内 τ**：每条线用 Kendall τ-b（能处理并列）比对模型顺序和标准位置，按每条线的块对数加权平均。**门槛：两本书都 ≥ 0.8。**
- **片段级 τ**：把同一片段内部的块对去掉再算一遍。这些块对是按原文顺序排的，本来就不会错，去掉以后是模型自己排出来的真实水平。只记录。
- 只记录、不设门槛：线的条数和每条线的块数、未分配数、被删的回有没有标成缺口（人工判）、被截断的回有没有标成断点、调用次数和费用。
- 冷门书没到 0.8：停下来报告，跟作者商量，不自己改提示词重跑。
- 验收脚本 `tools/eval_threads.py`，不调模型，只读书文件夹和答案，写报告文件。

### 6.3 费用

真跑前按实测参数细算（场景卡每卡约 6.6k 输入、约 1.75 次调用，来自 ②a 验收），报给作者，同意再跑。粗估两本合计 $1 左右。

## 7. 测试

- 全部用 `FakeBackend`，不联网、不花钱。
- 单元测试：压行（规范名替换、三类分流）、片段绑定与断开、覆盖校验（漏 / 重 / 编造）、3 次后的收尾、大书分段、编号只增不减、确认线在重跑时保留、`pending`、输入指纹不一致记 `outdated`、作者的每个操作、Kendall τ-b（手算样例）、标准位置换算。
- 集成：假模型返回把步骤 6 完整跑一遍，含暂停后重跑走缓存。

## 8. 跟总 spec 的偏差

1. **计划②拆成 ②a / ②b / ②c**，步骤 7 放到 ②c。
2. **提纲、设定笔记不参与排序**：提纲挂线、笔记挂世界。总 spec 没区分类型。
3. **同一文件相邻的正文块绑成片段再排**，模型可以拆。总 spec 没有这一条。作者说自己的稿子里「单个文件内部顺序靠谱」和「很多片段乱贴」两种情况都有，所以绑定是软的。
4. **全书统一的时间单位在 2.1 定**；全书只有一条主线，取块最多的世界的主线。总 spec 只说「单位由模型按本书提议」「指定一条主线」，没说在哪一步、几条。
5. **确认过的线重跑时保留**，模型的新建议进 `pending`，照 ②a 实体的做法。
6. **用输入指纹判断跑的途中上游有没有变**，修已知问题文档里那条。
7. **验收加一本冷门书**，两本都要过 τ ≥ 0.8；另报片段级 τ。
