# 理稿台 计划④ 设计：二期「取舍」——矛盾裁决、取舍看板、成书骨架、导出

- 日期：2026-09-22
- 上位文档：`2026-09-10-ligaotai-design.md` 第 7 章（本文细化并局部改写它，冲突处以本文为准）
- 前置：计划①②③ 已完成（步骤 1–7 + 一期界面）

## 1. 要解决什么

一期把乱稿理成了「场景 + 场景卡 + 线 + 档案 + 矛盾」。二期让作者**做决定并先读到一本书**：定下矛盾的说法、决定每条线的去留、排出卷章骨架、把现成场景按骨架拼成一本可以从头读到尾的书，缺的地方留醒目的空洞。三期（补写）直接用二期的骨架和空洞说明，本文只保证数据够用，不做补写。

## 2. 范围

**做**：矛盾裁决与定稿设定、取舍看板（含 AI 建议与影响检查）、成书骨架（生成 + 编辑）、导出 md / txt、对应的界面页。

**不做**：
- 补写（三期），包括「点空洞进入补写」。
- 改原稿正文。裁决只记录「另一边要跟着改哪些场景」，不改原文。
- 导出 docx / EPUB。
- 故事时间线冲突检查（仍在待办，理由见 `已知问题与待办.md`）。
- 界面上的任何费用数字（沿用计划③ spec 第 7.3 节）。

## 3. 已定的决定（2026-09-22 作者拍板）

1. **一份 spec、一份计划、内部分五个里程碑**，每个里程碑做完都能单独用。
2. **伏笔影响按需问模型**：拖进「砍掉 / 合并」的那一刻只对这一条线调一次，按签名缓存；不加全书伏笔配对步骤。
3. **骨架由程序排顺序，模型只分卷分章、起名、写空洞说明。**
4. **看板上还有「还没想好」的线时照样能生成骨架**：当保留处理，并在骨架上标出来。
5. **设计不绑定任何编辑器**：数据是书文件夹里的普通 md / json，任何文本编辑器都能打开。

## 4. 总体结构

- **不加流水线步骤**。步骤 1–7 不变。二期是作者驱动的操作：点了才跑；要调模型的（AI 建议、影响检查、生成骨架）走现有 `JobRunner`，界面照旧用全局 job store 显示进度、禁用会打架的按钮。
- **后端新模块**（按「一个文件一件事」拆）：
  - `verdicts.py`：写裁决、派生 `定稿设定.json`、算「要跟着改的场景」
  - `triage.py`：看板读写与对账、程序化影响、AI 建议与伏笔影响（模型部分）
  - `skeleton.py`：排序交织、空洞插入、分章（模型）、空洞说明（模型）、编辑操作
  - `export.py`：按骨架拼书
- **新提示词**：`prompts/triage_advice.md`、`prompts/triage_impact.md`、`prompts/skeleton_chapters.md`、`prompts/skeleton_holes.md`。
- **引用编号核对复用档案那套**（`archive.check_archive` 的编号规则）：模型写出的每个场景编号必须真实存在、且在允许范围内，不合规就带着问题重试。

## 5. 里程碑 1：矛盾裁决（不调模型）

**已有基础**（计划②c 留好的位子，别重造）：`矛盾.json` 每组已有 `verdict`（空）、`verdict_sig`、`verdict_stale` 字段；组编号 `C-xxx` 由 `id_registry` 按 (规范主语, 属性) **永久固定**；重跑时 `verdict` 按 (主语, 属性) 自动迁移，值集合跟下判定时不同就标 `verdict_stale`，迁不上的进 `orphan_verdicts`。

**裁决形状**（写进组的 `verdict`，同时把 `verdict_sig` 设为当前 `values_sig`、`verdict_stale` 清掉）：

```json
{"kind": "pick", "value": "二十二", "note": "", "by": "author", "at": "2026-09-22T15:00:00+08:00"}
{"kind": "own", "value": "十九", "note": "作者自己定", "by": "author", "at": "..."}
{"kind": "later", "by": "author", "at": "..."}
```

- `pick` 的 `value` 必须是该组 `values` 里的某个值，否则 400。
- `later` 只表示「看过了，先放着」，不进定稿设定。
- 撤销裁决：`verdict` 置回 `null`。

**定稿设定**（`定稿设定.json`，每次裁决后整体重写）：只收 `pick` / `own` 且不 stale 的组。每条：`{"id": "C-001", "subject", "attribute", "value", "sources": [支持这个值的场景编号], "note"}`；`own` 的 `sources` 为空。

**要跟着改的场景**：对 `pick` / `own`，列出该组里其他值出现的场景（编号 + 原句 quote）。只展示，不改原文。

**并发**：有任务在跑（尤其步骤 7 在重写 `矛盾.json`）时写裁决的接口返回 409，界面按钮本来就被 job store 禁用。

**界面**：矛盾页每组加操作——每个值一个「以此为准」按钮（不写死左右，值有几个就几个）、「都不对，我自己写」（输入框）、「先放着」、已裁决的显示结论和「撤销」；`verdict_stale` 的组醒目提示「值变了，请重看」。页头加一个筛选：全部 / 未裁决 / 需重看。

## 6. 里程碑 2：取舍看板

### 6.1 看板数据

`取舍/看板.json`：

```json
{"cards": {"L-001": {"col": "keep", "merge_into": null, "note": ""},
           "L-002": {"col": "merge", "merge_into": "L-001", "note": ""}}}
```

- 列：`keep`（保留）/ `merge`（合并）/ `cut`（砍掉）/ `undecided`（还没想好）。**新出现的线默认 `undecided`**。
- `merge` 必须带 `merge_into`，且指向另一条不在 `cut` 的线；否则 400。被并入的线后来被砍掉或消失 → 这张卡标「合并目标失效」。
- **对账**：每次读看板都按 `世界与支线.json` 的线编号对一遍。线消失 → 卡保留、标 `orphan`（界面灰显，可删）；新线 → 加一张 `undecided`。

### 6.2 卡片内容

程序直接给：线名、世界、字数（该线主版本场景字数和）、场景数、完结 / 待定（`end.state`）、缺口数、是否主线、排序是否失败。

**AI 建议**：作者点「让 AI 给建议」时，**所有线一次调用**（综合档）。输入：每条线的档案「一句话 + 来龙去脉」段落（没有档案的线退回用 `about`）、全书地图、各线字数与完结状态。输出每条线 `{"thread", "advice": "keep|merge|cut|flashback", "merge_into"?, "reason"}`，`reason` 要带场景编号并核对。`flashback` 是「改成回忆」，只作建议，看板上仍放在保留列由作者决定。按签名（输入文本 + 提示词）缓存，没变不重跑。

### 6.3 影响检查

卡片被拖进 `cut` 或 `merge` 时触发，结果显示在卡片旁，作者看完再决定要不要留在这一列（拖回去即撤销，不需要额外确认）。

**程序化部分**（不花钱，立刻出）：
1. **交汇点**：`世界与支线.json` 的 `intersections` 里涉及这条线的，列出对方线和场景。
2. **只在这条线出场的人物**：用 `实体.json` 把卡片 `characters` 归到规范名，统计每个人物出场的线；只出现在这条线（且角色是主要 / 次要）的列出来。
3. **别处对这条线事件的引用**：别的线的场景卡 `refs_elsewhere` 里，跟这条线的场景卡 `events` / `summary` 共享实体规范名的条目。**这是启发式**，界面上标「可能」。

**模型部分**（按需一次调用，综合档）：输入这条线各场景的 `hooks_planted` / `hooks_resolved`（带场景编号），和其他未砍线的 `hooks_resolved` / `hooks_planted`。让模型配出「这条线埋、别的线收」和「别的线埋、这条线收」的伏笔对，每对必须引用两端真实场景编号并核对；最后写一段「砍掉 / 合并后怎么补救」。
- 合并时的补救建议要针对 `merge_into` 那条线写。
- 缓存签名 = 输入文本 + 提示词 + 列（cut / merge）+ `merge_into`。看板上别的卡变了只要不影响输入（被砍的线不再作为「收的一端」参与）就不重算；影响了就重算。

**界面**：原型的四列看板。卡片之间用原生 HTML5 拖放（不引库）；每张卡另有一个「移到…」下拉框，键盘可用、测试也走它。合并时弹出选「并入哪条线」。

## 7. 里程碑 3：成书骨架

### 7.1 数据

`取舍/骨架.json`：

```json
{"generated": "...", "by": "program|author", "volumes": [
  {"title": "第一卷 ……", "chapters": [
    {"title": "……", "items": [
      {"type": "scene", "id": "S-0001"},
      {"type": "hole", "id": "H-001", "gap": "Q-003", "task": "……", "after": "S-0001", "before": "S-0002"}],
     "notes": [{"kind": "undecided", "thread": "L-003"},
               {"kind": "merge", "thread": "L-002", "into": "L-001"},
               {"kind": "cut_crossing", "thread": "L-004", "scene": "S-0066"}]}]}],
 "unplaced": {"scenes": [{"id": "S-0120", "why": "no_time|unaligned_thread"}],
              "holes": [{"id": "H-020", "gap": "Q-077", "why": "no_anchor"}]}}
```

空洞编号 `H-xxx` 在一份骨架内唯一；作者新增的空洞没有 `gap`。

### 7.2 生成：程序先排一整串

1. **参与的线**：看板上 `keep` / `merge` / `undecided` 的线；`cut` 的不参与。
2. **场景**：参与线的场景，版本组只取主版本。
3. **全局时间** = 线 `offset` + `times[sid].t`（沿用 `lib/segments.ts` 的规则，后端写一份等价实现并用同样的手算用例测）。按全局时间排序；同一时刻主线优先，再按线编号，再按线内原顺序。
4. **放不进时间轴的**进 `unplaced`：线 `offset` 为 `null`（没对齐主线）的整条线、`t` 为 `null` 或缺键的场景。
5. **空洞**：参与线的缺口，按 `before` / `after` 锚点插在对应场景前后；两个锚点都缺的进 `unplaced.holes`。只属于被砍的线的缺口不插。
6. **备注**：`undecided` 线的场景所在章挂 `undecided`；`merge` 线挂 `merge`；主线上跟被砍线的交汇场景挂 `cut_crossing`。

### 7.3 生成：模型分卷分章、起名

- 输入：排好的序列，每项一行「序号 · 编号 · 所属线 · 字数 · 摘要」（空洞一行写「空洞 · 缺口事件」）。
- 输出：卷的切分点、章的切分点（用序号）、每卷每章的名字。
- **程序核对**：切分点单调递增、覆盖整串、每项恰好属于一章、不改顺序；不合规就把问题带回去重试（`llm.chat_json` 现有的 `max_attempts`）。重试到底仍失败 → 退回**程序兜底切法**（按字数每章约 1 万字、每卷约 10 章，章名用首个场景摘要的前 12 字），报告里写明「分章用了兜底」。
- **大书分窗口**：序列超过输入预算时按窗口切（窗口间重叠 10 项做衔接），各窗口结果拼接后再整体核一遍。预算照归线的做法放进书设置：新增 `skeleton_max_input_tokens`，默认 600000（跟 `threads_max_input_tokens` 同一估法）。

### 7.4 生成：空洞任务说明

每个空洞一段说明：在哪两块之间、要写什么、原稿里哪些场景提到过这件事（`mentioned_in`）。输入是缺口事件、前后场景摘要、`mentioned_in` 场景的摘要。**一次调用处理一批空洞**，每段必须引用真实编号并核对。失败的空洞用程序拼的说明兜底（「在 S-A 与 S-B 之间补写：<缺口事件>；原稿提到于 S-x」）。

### 7.5 编辑

改卷名 / 章名；拖动章的顺序（跨卷也行）；在章之间挪场景 / 空洞；新增空洞（手写任务说明）；删空洞；把 `unplaced` 里的场景拖进某章。任何编辑后 `by` 变 `author`。

**重新生成会覆盖手改**：`by == "author"` 时界面先确认；后端生成前把当前文件复制成 `骨架.bak.json`。

**对账**：骨架里引用的场景被移除（原稿删了）或所属线后来被砍 → 那一项标 `missing` / `cut`，界面灰显提示，不自动删。

### 7.6 界面

原型「成书骨架」一节：左边卷章树，右边选中章的条目列表；空洞红框，展开显示任务说明（可改）；章上的备注用小标签。顶部「生成骨架」「导出」两个按钮。

## 8. 里程碑 4：导出

- 按骨架顺序拼：卷名做一级标题、章名做二级标题；场景正文取原稿原文（主版本）；空洞处插占位块：

  ```markdown
  > 【空洞 H-003】在 S-0012 与 S-0013 之间补写：……
  ```

- md 在每块场景前加一行 `<!-- S-0030 -->`，方便对回原稿；txt 不加注释，标题不用 `#`，空洞用 `【空洞】……` 一段。
- `unplaced` 的场景和空洞放在书末「附：未定位」一节。
- 导出文件名用书的标题（非法字符替换掉），覆盖上一次导出。
- 界面：导出完成后显示两个文件的路径和字数，并提供下载链接（后端加一个只读的下载接口）。

## 9. 接口（新增）

| 方法 | 路径 | 作用 |
|---|---|---|
| PUT | `/api/books/{name}/contradictions/{cid}/verdict` | 写 / 撤销裁决 |
| GET | `/api/books/{name}/canon` | 读定稿设定 |
| GET | `/api/books/{name}/contradictions/{cid}/followups` | 要跟着改的场景 |
| GET / PUT | `/api/books/{name}/triage/board` | 读（含对账）/ 改一张卡 |
| POST | `/api/books/{name}/triage/advice` | 生成 AI 建议（任务） |
| GET | `/api/books/{name}/triage/impact/{tid}` | 程序化影响（即时） |
| POST | `/api/books/{name}/triage/impact/{tid}` | 伏笔影响（任务） |
| GET / PUT | `/api/books/{name}/skeleton` | 读 / 整份保存编辑后的骨架（后端校验结构） |
| POST | `/api/books/{name}/skeleton/generate` | 生成骨架（任务） |
| POST | `/api/books/{name}/export` | 导出 |
| GET | `/api/books/{name}/export/{fmt}` | 下载导出文件 |

**本计划新增的所有写接口**，只要有任务在跑（不分是不是这本书）就返回 409，不做读-改-写（照 `archive_rerun` 的做法；现有接口并非全都这样，不在本计划里统一）。坏文件报具体文件名（沿用计划③ 修过的做法）。

## 11. 出错处理

- 手改坏的 `看板.json` / `骨架.json` / `定稿设定.json`：读接口报 500 带文件名，不静默当空（这些是作者的决定，当空会丢）。`缓存.json` 坏了当空（只是多花钱）。
- 模型输出不合规：带问题重试；到底失败时，已经拿到的部分保留，失败项进任务结果的 `failed`，界面列出。
- 生成骨架时上游数据（线 / 看板）在跑的途中被改：跑完比对输入指纹，变了就不写入并报「输入变了，请重新生成」（沿用步骤 6 的 `input_changed` 做法）。

## 12. 测试

- **手算钉死的期望值**（实现算错测试当场红，断言不许为迁就实现而改）：用雪月梅真数据的 fixture 手算全局时间交织顺序的前 10 项、缺口插入位置、`unplaced` 的数量。
- 单元：裁决写入与迁移（重跑后 stale、orphan）、定稿设定派生、看板对账（线消失 / 新增 / 合并目标失效）、程序化影响三项、分章结果核对（重复 / 漏项 / 乱序三种坏输出各一条）、兜底切法、导出格式（md 注释、txt 无注释、空洞占位、未定位附录）。
- 模型调用一律用假 caller 测；**测试里用真实数据契约**（`实体.json` 的 `type` 是 `person/location/organization`，不是中文——②c 在这里翻过车）。
- 前端：每页组件测试 + 看板「移到…」下拉路径。

## 13. 验收（里程碑 5，拿《雪月梅传》验收书）

**程序核的硬判据**：
1. 看板全部 `keep` 时，导出的书里每块参与场景（主版本）**恰好出现一次**。
2. 导出场景顺序跟原书顺序的 Kendall τ ≥ 0.9。
3. 骨架里的空洞数 = 能定位的缺口数（参与线的、至少一端有锚点的）。
4. 把 L-002 设为 `cut`：程序化影响里包含它在 `intersections` 里的全部交汇点；导出的书里不含 L-002 的场景，也不含只属于 L-002 的缺口。
5. 所有模型输出里的场景编号 0 条编造。

**作者人工抽查**：伏笔影响配对（抽 L-002）、分卷分章是否像样、空洞说明是否说得清。

**界面**：新增和改动的页面照计划③ 的做法真书截图，浅色深色各过一遍、窄窗口过重点页；Console 无报错。

**开跑前先发一次 5 token 的 ping 验 key**（计划②c 撞过 key 失效）。
