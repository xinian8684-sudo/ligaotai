# 理稿台：故事时间线冲突检查 设计

日期：2026-09-28
状态：作者已逐段确认设计，待写实施计划

## 1. 要解决什么

矛盾扫描（步骤 7）只管「同一个主语、同一个属性写了不同的值」，比如小梅的年龄前后倒退。它管不到**跨场景、跨人物的时间逻辑**。总设计（`2026-09-10-ligaotai-design.md`）里写了一句「另外检查故事时间线上的冲突」，②c 起一直推迟，理由是故事时间估不准。

本期只做两类（作者 9-28 定：四类都要，先做这两类）：

- **A 人死了又出场**：某人在前面的场景里已经死了，故事时间更晚的场景里他又活着在场。
- **C 提前知道后面的事**：某场里提到、回忆的一件事，按故事顺序要到后面的场景才发生。

以后再做：B 时长 / 节令对不上、D 同一时刻身在两地。

**一个前提要讲清楚**：理稿台的故事顺序是模型排的，会排错（9-28 实测雪月梅主线线内 τ 约 0.96，第 16 回的比箭排到了第 12 回前面）。所以报出来的冲突有两种可能：作者真写错了，或者我们的顺序排错了。界面和裁决都按「两种都可能」来设计，不替作者下结论。反过来，C 类也能当「顺序排错」的探测器。

## 2. 放在哪、什么时候跑

- **不进流水线**。矛盾页加一个分页「时间线」，有「检查时间线」按钮，作者想查就点（走全局 job store，跟别的任务互斥）。
- **前提**：步骤 6（归线）是 done。否则按钮禁用，并说明原因。
- **故事顺序**：用 `skeleton_order.build_sequence`（骨架用的同一个函数），传空看板、不砍线，所有线都参与。排不进时间轴的块（没时间、没对齐主线、没归线）不参与检查，结果里记个数：「N 块没有故事位置，没查」。
- **结果**：`<书>/时间冲突.json`（跟 `矛盾.json` 一样放在书的根目录）。
- **过期**：结果里存输入指纹（故事顺序 + 参与的场景卡内容 + 实体规范名）。作者改了线的顺序、合并拆分了线、重做了卡、改了实体规范名以后，GET 时指纹对不上，分页顶上提示「顺序或场景卡变了，结果可能过时，建议重查」。旧结果照样显示。

## 3. 找嫌疑（纯程序，不调模型）

输入：参与检查的场景按故事顺序排好的列表 `seq`（位置 `pos[sid]`）、每张主版本场景卡、实体规范名映射 `canonical_map`。

### 3.1 A 人死了又出场

1. 从卡的 `facts` 里挑「死了」的条目：attribute 是「生死」，或者 attribute / value 里出现死亡词（死、亡、故、殁、卒、斩、阵亡、身故、归天……，词表放常量，拿雪月梅真卡过一遍）；**排除**明确不是死的值（「免死」「未死」「被擒」「监禁」这类，同样是常量词表）。拿不准的留给模型（3.1 只负责缩小范围）。主语过 `canonical_map` 归一。
2. 每个人取**最早**的那条死亡记录所在场景 D（故事顺序最靠前的）。
3. 找故事顺序排在 D 后面、`characters`（同样归一）里有这个人的场景 Y。每一对 (D, Y) 是一个嫌疑。同一个人后面出现多次的，每个 Y 都算一个嫌疑（模型会逐个判「在场 / 只是被提到」）。
4. 上限：一个人最多取离 D 最近的 5 个 Y（防止主角误判「已死」时嫌疑爆炸），截掉的数记进结果。

### 3.2 C 提前知道后面的事

1. 每张卡的 `refs_elsewhere` 里每一条是一个「回指」R，所在场景 S。
2. 给 R 挑候选场景：跟 S 有共同人物（归一后）的其他场景，按共同人物数排序，同分按跟 S 的故事距离近的排前，取前 8 个。同一条线上的优先（同分时排前）。
3. **只问可能有问题的**：候选里一个排在 S 后面的都没有，就不问模型，直接当没事——事情就算发生在候选里，也是在 S 之前。
4. 候选为空的回指跳过，记数。

## 4. 模型判（综合档，分批）

照矛盾扫描的做法：一批问多条，每条带编号，缓存按提示词 + 输入签名，失败的批次记进 `failed` 不中断。

### 4.1 A：他在后面那场里是死是活

输入每条：人名、D 场里提到他死的原文摘录（那条 fact 的 quote，加前后各一句）、Y 场里提到他的几句原文（按名字和别名在正文里找，最多 3 处，每处前后各一句）。

输出每条：`status` 三选一——`在场`（活着出现、说话、行动）、`提到`（只是别人说起、回忆、梦里、祭奠）、`说不准`；`reason` 一句话，带场景编号。

`在场`、`说不准` 报成冲突，`提到` 丢掉（不存）。

### 4.2 C：这件事是在哪一场发生的

输入每条：回指原话 R、S 场的摘要、候选场景（编号 + 摘要，按 3.2 的顺序）。

输出每条：`happens_in` 是候选里的一个编号或 `null`（都不是 / 看不出来）；`reason` 一句话。

`happens_in` 不在候选里算格式错，重试。`happens_in` 排在 S 后面 → 报冲突；在 S 前面或 null → 不报。

### 4.3 每条冲突存什么

```json
{"id": "T-003", "kind": "A", "who": "劉公", "ref": null,
 "scenes": ["S-0021", "S-0046"], "pos": [12, 30],
 "quotes": ["……劉公已死……", "……劉公道……"],
 "reason": "……[S-0021][S-0046]", "status": "在场",
 "sig": "<kind+scenes+who/ref 的签名>",
 "verdict": null, "verdict_sig": null}
```

C 类 `who` 为 null、`ref` 是回指原话，`scenes` 是 [回指所在场, 事情发生场]。编号 `T-` 按 sig 登记、永久固定（学 `矛盾.json` 的 C 编号），重查时同一个 sig 沿用编号和裁决。

## 5. 裁决和界面

- 分页顶上一行：待看 N、写错了 N、排错了 N、已忽略 N；过期提示；没参与检查的块数；有失败批次时说明。
- 每条一张卡：类型标签（「人死了又出场」「提前知道后面的事」）、人名或回指原话、两场编号（`SceneRefs` 可点，跳场景浏览）、两场在故事顺序里的位置（「第 12 位 / 第 30 位」）、两句原文、模型的一句说明。
- 三个按钮：**确实写错了**、**是顺序排错了**、**没问题，忽略**；可以改、可以撤。标「是顺序排错了」的旁边给链接到归线页（不自动调顺序，作者 9-28 定的）。
- 裁决跟着 `sig` 走：重查时同一条（两场编号 + 类型 + 人名 / 回指原话都没变）沿用裁决。sig 对不上的旧裁决丢掉（冲突本身已经不存在了）。
- 过滤：默认只看「待看」，可切换看全部。
- 界面上不显示任何费用数字（计划③ 的规矩）。

接口：`POST /api/books/{name}/timeline/run`（job）、`GET /api/books/{name}/timeline`（结果 + 是否过期）、`PUT /api/books/{name}/timeline/{tid}/verdict`（`{"kind": "author_error" | "order_error" | "ignore" | null}`）。

## 6. 验收

### 6.1 造题（`tools/scramble.py`）

- **A 植入 5 处**：从人物名单里挑人，要求他在两个不同章节 a < b 里都有名字出现、b 章里他有对话（名字后面紧跟「道」「說」「问」这类字，程序判），在 a 章他出现的那一句后面插「某某染病身亡。」（按原文繁简）。答案记 `{kind: "A", who, chapters: [a, b]}`。避开会被截断、被别名替换的章节和人物（照矛盾植入的规矩）。
- **C 植入 5 处**：用一份手写的事件清单（`data/事件-雪月梅.json`，不进仓库，格式 `[{"chapter": 16, "who": "岑秀", "event": "比箭連中三箭"}]`），挑章节 a 早于事件章 b，在 a 章里 who 出现的那一句后面插「{who}想起那日{event}之事。」。答案记 `{kind: "C", who, event, chapters: [a, b]}`。
- 植入方向改好的年龄矛盾照旧植入（9-28 改完还没重跑验证），一轮乱稿三种植入一起验。

### 6.2 判卷（`tools/eval_timeline.py`）

- **召回**：A、C 分开算。A 命中＝报出的某条 A 类冲突，who 对得上（归一后），两场分别落在 a 章、b 章。C 命中＝某条 C 类冲突，第一场落在 a 章、第二场落在 b 章。门槛各 ≥ 4/5。
- **没命中的分原因**：A——a 章的卡里有没有抽出死亡 fact / b 章的卡人物名单里有没有他 / 模型判成了「提到」；C——a 章的卡 `refs_elsewhere` 里有没有这条回指 / 候选里有没有 b 章的场景 / 模型判错了场。
- **误报**：报出来的全部冲突逐条人工过（开发者先全部过一遍，再请作者抽查），区分「书里真有的时间问题」「我们的顺序排错」「模型判错」三类，只报数不设门槛（跟矛盾扫描的 `unmatched_true` 一样，验收书本身就可能有冲突）。
- **白捡的一道题**：雪月梅主线第 16 回比箭（S-0014，人物里有刘电）排在第 12 回（S-0127，刘芳托付刘电）前面。C 类如果报出这处，就证明它能当顺序排错的探测器；抓不到不算不过关。

### 6.3 花钱

真跑放在 DeepSeek 低峰时段（工作日 9–12、14–18 以外，周末节假日全天）。重新造乱稿、重跑步骤 1–7 加时间线检查，一轮。

## 7. 不做

- B 时长 / 节令、D 身在两地（以后再做）。
- 一键调顺序（先用裁决「是顺序排错了」+ 跳归线页）。
- 把时间线检查结果写进设定库 / 全书地图。
- 对 `t`（估的故事时间数值）做任何判断——只用先后顺序，不用时间数值，因为数值不硬（②c 以来的结论）。

## 8. 风险

- **死亡 fact 抽得不全**：9-21 实测 facts 对直白陈述的抽取率约 95%。验收的归因会把「没抽到」单独记出来，不算到检查头上。
- **人物名单混了「被提到的人」**：S-0087 的人物名单里就有早已去世的何式玉。所以 A 类必须经过模型判「在场 / 提到」，程序不直接报。
- **主角被误判「已死」**：比如「幾乎死了」被抽成生死。3.1 第 1 条的排除词表和第 4 条的上限兜住，模型再判一道。
- **顺序本身排错会制造 C 类冲突**：这正是界面要给「是顺序排错了」这个裁决的原因。
