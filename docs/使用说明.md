# 理稿台使用说明

这份说明写给第一次用理稿台的作者：手上有一大堆写了很多年、乱成一团的稿子，想把它理成一本书。不需要会编程，但要能照着敲几行命令。

## 理稿台能帮你做什么、不能做什么

**能做的**：把几百个乱命名的文件读进来，切成场景，找出同一场写过的几个版本，给每一场做一张卡片，认出同一个人的不同叫法，把场景分到各条故事线里、排出先后，再写出每条线的来龙去脉、每个世界的设定集、全书矛盾清单和全书地图。之后你在看板上决定哪条线留、哪条砍，理稿台排出成书骨架、标出要补写的空洞，最后导出成 Word / EPUB / Markdown / 纯文本。

**不能做的**：

- **不替你写书**。补写说明只告诉你「这里缺了什么」，正文还是你写。
- **不保证对**。所有 AI 产出都是草稿：顺序会排错、矛盾会漏报也会误报、人名会认错。理稿台的设计是「AI 先提，你来拍板」，每一处要你确认的地方都留了按钮。
- **不联网分享你的稿子**。程序只在你自己电脑上跑，界面只有本机能打开；但场景卡、归线这些步骤要把稿子的内容发给你配置的模型接口（默认 DeepSeek），介意的话换成你信得过的接口。

## 一、装好

需要三样东西：

1. **Python 3.11 或更新**，和 [uv](https://docs.astral.sh/uv/)（装 Python 依赖用）。
2. **Node.js**（只在第一次构建界面时要用，以后不用）。
3. **一个 OpenAI 兼容的模型接口的 key**。默认用 DeepSeek，去 DeepSeek 开放平台注册、充值、建一个 API key。

下载代码后，在仓库根目录打开终端：

```bash
uv sync                      # 装依赖
cd web
npm install                  # 下面三行构建界面，只要做一次
npm run build
cd ..
uv run python -m ligaotai    # 启动
```

浏览器打开 <http://127.0.0.1:8765/> 就是理稿台。关掉终端窗口程序就停了，下次只用敲最后一行。

## 二、配 key

打开界面左下角的「设置」，填接口地址（默认 `https://api.deepseek.com`）和 key，点「测试连接」，两档模型都显示成功就好了。

- **批量档**负责给每一场抽卡片，调用次数多，默认不开思考，比较便宜。
- **综合档**负责需要通盘考虑的判断（归线、排序、档案、矛盾），默认开思考。
- 书库目录也在这里改，默认是仓库下的 `书库/`。

key 存在仓库根目录的 `config.json` 里，这个文件不会被提交到 git。也可以设环境变量 `LIGAOTAI_API_KEY`。

## 三、准备稿子

把所有稿子放进一个文件夹（可以有子文件夹）。支持 `.txt`、`.md`、`.docx`，编码 UTF-8 和 GBK 都能自动认。不用改文件名，也不用排好顺序——乱就是理稿台要处理的。

建议：

- 设定笔记、大纲、废稿都可以放进去，理稿台会把它们挂到对应的世界上，或者留在「没归到任何线」里让你看。
- 同一章有好几个版本也没关系，第 3 步会找出来让你挑主版本。
- **先拿一小部分试**（比如几十个文件），熟悉流程、看看费用，再导全书。

## 四、走一遍流水线

在「书架」建一本书，点「导入原稿」选文件夹。进书以后左边导航第一项是「理稿流水线」，一共 7 步，每步一个「跑」按钮，从上往下依次跑：

| 步 | 做什么 | 花钱吗 | 你要做什么 |
|---|---|---|---|
| 1 导入 | 读文件、认编码 | 不花 | 原稿改了可以再导一次，只处理改动过的文件 |
| 2 切场景 | 按章节标题、分隔符、空行切成场景块，每块一个固定编号 `S-0001` | 不花 | 无 |
| 3 查重 | 找出同一场写过的几个版本，自动挑主版本 | 不花 | 到「场景浏览」里核一下主版本挑得对不对 |
| 4 场景卡 | 每一场做一张卡片：摘要、人物、地点、时间线索、设定事实、提到的别处的事 | 花（按场景数） | 无 |
| 5 实体合并 | 把同一个人 / 地点 / 组织的不同叫法归成一组 | 花（少） | 到「实体确认」逐组接受或拆开 |
| 6 归线排序 | 分世界、分故事线、线内排先后、对齐到主线时间轴、找缺口 | 花（多） | 到「归线确认」处理拿不准的块，给线改名、设主线、合并或拆分 |
| 7 档案+矛盾+地图 | 每条线写一份档案，每个世界写一份设定集，扫全书矛盾，写全书地图 | 花（多） | 到「设定库」「矛盾」看结果 |

几点要知道的：

- **每一步都可以暂停、重跑**。跑过的部分有缓存，重跑不会重复花钱；改了上游（比如改了实体名），下游会标成「过期」，提醒你重跑。
- **你确认过的东西重跑时会保留**：确认过的实体组、确认过的线、矛盾裁决、看板上的去留。
- **跑失败了**：流水线页会列出失败项，多半是网络或接口问题，直接再点一次「跑」。第一次调用就报 401 是 key 失效了，换 key 再跑。

## 五、看结果

- **全景**：横轴是故事时间、每条线一道泳带，红色菱形是缺口（卡片里提到、但稿子里没写的事），数字是挤在一起的几个缺口，「2版」「3组」是那里有多版本的场景。跨度太大的空白会自动断开。点一条线看它写到哪了，点缺口看缺了什么。
- **场景浏览**：原文和卡片左右对照，可以搜编号、标题、摘要，也能勾上「也搜原文」。文字里出现的场景编号都能点，点了跳过来。
- **设定库**：每条线的档案、每个世界的设定集、全书地图。每句结论后面都带场景编号，方便回原文核对。
- **矛盾**：同一个人、同一个属性写成了不同的值（年龄、身份、关系……）。默认只展开严重的。每条可以「以某个值为准」「都不对，我自己写」或「先放着」，你定的值会写进定稿设定。
- **时间线**（在「矛盾」页的分页里）：点「检查时间线」，查两类问题——人死了后面又活着出场；一场里提到的往事，排在了它发生的那场前面。查出来的不一定是写错了，也可能是理稿台把顺序排错了，所以每条有三个选项：写错了 / 顺序排错了 / 忽略。这一步要先跑完第 6 步，而且比较贵（见下面「费用」），可以不跑。

## 六、取舍、骨架、导出

- **取舍看板**：四列——保留 / 合并 / 砍掉 / 还没想好。点按钮让 AI 给每条线一个建议；把线拖进「砍掉」或「合并」，会马上列出会断掉的东西（跟别的线的交汇点、只在这条线出场的人物、可能相关的引用）。伏笔影响要单独点「检查伏笔影响」才会调模型。
- **成书骨架**：点「生成骨架」，程序按故事顺序把留下的线排成卷和章，模型起章名、给每个空洞写补写说明。骨架可以手改：拖动场景和章调顺序，删空洞、加空洞。原稿后来变了的条目会标出来。
- **导出**：骨架页「导出成书」，可以选 Markdown、纯文本、Word（.docx）、电子书（.epub）。空洞会以补写说明的形式留在正文里，提醒你哪里要补。

## 七、费用

理稿台按你接口的实际用量花钱，**界面上不显示任何费用估算**——这个项目里事前估价反复失准，宁可不给。实际用量记在每本书的 `book.json` 里，以接口后台的账单为准。

参考：开发时用 DeepSeek（`deepseek-flash`，几乎全在闲时）把整本《斗破苍穹》（1651 章、458 万字，打乱成 2900 个文件）完整理一遍。按每一步最后一次成功跑的实际花费加起来，大约 **¥120–130**：

| 步骤 | 约 |
|---|---|
| 场景卡 + 实体合并 | ¥20 |
| 归线排序 | ¥23 |
| 档案 + 矛盾 + 地图（含伏笔配对） | ¥20–25 |
| 时间线检查 | ¥57 |

- 一本 200 万字的书没有实测过，按上面粗估在 **¥50 上下**（时间线检查有一步随字数平方增长，书短一半它降得更多）。
- DeepSeek **白天高峰价大约贵一倍**，长任务挑闲时跑。
- 最省钱的做法是**不跑时间线检查**，它将近占一半。
- 改 `prompts/` 下的提示词会让相关缓存全部失效；尤其是 `cards.md`，改一个字全书每一场都要重抽卡。

## 八、你的数据在哪

每本书是书库目录下的一个文件夹，里面全是普通的 md / json，用文本编辑器就能打开：

| 文件 / 文件夹 | 是什么 |
|---|---|
| `原稿/` | 导入时拷进来的原稿副本，不会改你原来的文件 |
| `场景/` | 切好的场景块（原文，永不修改） |
| `场景卡/` | 每场一张卡 |
| `实体.json` | 人物 / 地点 / 组织和它们的叫法 |
| `世界与支线.json` | 归线结果：世界、线、线内顺序、缺口、交汇点 |
| `档案/` | 线档案、世界设定集 |
| `全书地图.md` | 全书地图 |
| `矛盾.json` / `时间冲突.json` | 矛盾和时间线冲突，连同你的裁决 |
| `book.json` | 每一步的状态、书的设置、用量 |

备份就是拷整个书文件夹。

## 九、准确率：心里要有数

理稿台是拿打乱的公版小说和网文验收的（把原书拆成几百个乱命名的文件、删章、截断、加别名、植入重写版和人造矛盾，再看能理回来多少）。下面是当时的成绩，**不代表你的稿子也能做到**：

- **查重**：《西游记》植入 15 个重写版，15 个全找到，没有误合并。
- **故事顺序**（理出来的顺序和原书顺序的一致程度，Kendall τ，1 是完全一样）：《西游记》约 1.0，冷门的《雪月梅传》全局约 0.89；整本《斗破苍穹》主线约 0.91。网文这种一条主线写到底的书，错的大头是把场景分进了错的「卷」。
- **矛盾**：植入 10 处年龄矛盾召回 8–9 处，引用编造 0 条。植入的矛盾写得很直白，这是下限测试。
- **时间线检查**：植入的 5 处「死了又出场」全抓到、5 处「提前知道后面的事」抓到 4 处；整本《斗破苍穹》报出来的 591 条冲突里，约三分之二确实是顺序排错了；之后改了判断规则，抽五分之一重跑，报对的比例到了约四分之三（全本没有重跑）。

所以：**排出来的顺序要过目，矛盾和冲突清单当线索用，不要当结论用。**

## 十、已知的局限

- **主线自己的个别错位救不回来**：线内排序排 5 遍按多数票合并，偶发的错能投掉，但模型每遍都犯的那几处投不掉。
- **长书的卷分错**：几千场的线会先分卷再卷内排，卷与卷的章节范围重叠时，块会归错卷。
- **伏笔**：同一个悬念在不同场里有好几种说法，合并做了，但会偶尔合过头或没合上。
- **时间线检查**只做了两类（死了又出场、提前知道后面的事），时长 / 季节对不上、同一个人同时在两地还没做。一件事发生过好几次（好几场拍卖会）时，模型常配到后面那次，产生误报。
- **跨线引用的影响检查**只用「只在这条线出场的人物」匹配，漏报在所难免，不是「保证找全」的清单。
- **单人单机**：只监听本机，只支持一个进程。
- **没有真作者用过**。目前所有验收都是拿公版书造的乱稿，真稿子会撞出什么问题，还不知道。

完整的待办和每条的来龙去脉见 [`已知问题与待办.md`](已知问题与待办.md)，每一阶段的验收过程见 [`验收记录/`](验收记录/)。
